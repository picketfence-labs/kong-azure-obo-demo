# ADR-0002: MCP/LLMルートのネットワーク分離方式

- **日付**: 2026-09-01
- **状態**: 決定

## コンテキスト
`docs/design-brief.md`の「3. アーキテクチャ」は、LLM（Azure OpenAI）アクセス用Routeについて「追加認証は掛けない。Docker Composeの内部専用ネットワークでNext.jsアプリ以外からアクセスできないようにすることで保護する」と定めている。MCPエンドポイント用Routeも、ブラウザではなくNext.jsエージェント（サーバーサイド）のみが呼び出す経路である点は同様。

しかし、Kong Gatewayの実装（`kong-ee/kong/templates/nginx_kong.lua`）を確認したところ、`proxy_listen`に設定した複数のlisten portは**単一のnginx `server {}`ブロック**が`listen`ディレクティブを複数持つ構成であり、Route/Serviceはどの`proxy_listen`ポートから着信したかに関わらず同一に評価される（Kong OSS/EEにNginxレベルでの「このRouteはこのポートのみ」という紐付け機構は存在しない）。したがって、Docker Composeで一部のポートだけをhostに公開しない、という対策だけでは「そのポートが公開されている限り、それ経由で全Routeに到達可能」という前提が崩れず、design-briefの文言をそのまま額面通りには実現できない。

この事実確認を経て、実現方式を利用者に提示し確認を取った。

## 検討した選択肢

1. **Kongを2インスタンス構成にする**: Chat UI/ログイン用Routeのみを持つKongコンテナ（ポート公開・ブラウザ到達可）と、MCP/LLM Route専用のKongコンテナ（docker-internalネットワークのみ、ポート非公開）に分割する。design-briefの「内部専用ネットワーク」を文字通り実現できる唯一の方式。ただしKong構成が2系統になり、decK管理対象ファイルも2つに分かれ、Postgres DBスキーマ共有や2重デプロイの複雑さが増す。
2. **単一Kongインスタンス＋`ip-restriction`プラグイン**: MCP/LLM RouteにOSS/EE標準の`ip-restriction`プラグインを付与し、Docker Compose内部ネットワークのCIDRのみを許可する。ポート自体は技術的には公開されたままだが、送信元IPで実質的に外部到達を防げる。構成はシンプルだが「ポートは開いている」点の説明が必要。
3. **単一Kongインスタンス＋ポート非公開のみ（簡易）**: Kongの2つ目の`proxy_listen`ポートをDocker Composeで`ports:`に含めずhost非公開のままにする。上記の通りRouteはポート非依存で相乗り到達可能なため、ブラウザ側Routeのポートが公開されている限り、パスさえ知っていれば同じポート経由でMCP/LLM Routeにも到達でき、実質的な分離にはならない。デモの簡便さを優先し、セキュリティ上の隙を許容する場合のみ選択する。

## 決定
選択肢3（単一Kongインスタンス＋ポート非公開のみ）を採用する。利用者に3案を提示し、明示的にこれを選択した。

## 判断基準・根拠
本デモは`docs/design-brief.md`が明記する通りローカルDocker Compose上の検証環境であり、CI化・本番運用は明示的にスコープ外（「将来」節）。利用者は選択肢3の「実質的な分離にはならない」というトレードオフを理解した上で、構成の単純さ（Kong 1インスタンス・decK管理ファイル1系統）を優先する判断を下した。

## 想定していたこと vs 実際どうだったか
design-briefの文言（「内部専用ネットワークで保護する」）は、Kongの`proxy_listen`がポート単位でRouteを制限できることを前提としているように読めたが、実際にはKongにその機構は無く、文言通りの保護は単純なポート非公開だけでは実現できないことが実装前の調査で判明した。この点は事前に利用者へエスカレーションし、本ADRとして記録した。

## 影響・トレードオフ
- MCP/LLM Routeは、パス（`/customers/mcp`、`/llm`等）を知っていればブラウザ側の公開ポート経由でも到達可能（OIDC OBOやACL自体の認証・認可はそのRoute固有のプラグインチェーンで引き続き機能するため、無認証で素通りするわけではない。ここで失われるのは「ネットワーク到達性そのものを断つ」という多層防御の1層のみ）
- 将来、本番相当環境やKonnect移行を検討する際は、選択肢1（Kong複数インスタンス）または選択肢2（`ip-restriction`）への移行を再検討する必要がある
